# TerraPi deployments

**Build and test** runs on pull requests and pushes to `main`. Pull requests use disposable credentials. A successful main build publishes the tested frontend, monitoring and notifier images to GHCR by digest and saves the controller bundle and release metadata as the `terrapi-release` artifact for 90 days. **Deploy → Run workflow** rolls out the latest successful main release in one workflow run. An optional build run ID selects a specific release for rollout or rollback. The VPS job prepares and verifies the broker, monitoring service and frontend. The Pi job then deploys and verifies the controller from the same build. Components already verified stay on the selected release.

## Private production configuration

Use the GitHub Actions environment `production-vps` for the VPS job and `production-pi` for the Pi job. Entries labeled Production below are needed in both environments. Apply the production approval rules required for both targets. Restrict both environments to the protected `main` branch. Limit who can approve changes to workflows and deployment scripts. Put **every deployment-specific value in Environment Secrets**, including hostnames, ports and account names. Public workflow names, run IDs, artifact names and source files contain only generic identifiers. The browser uses its current origin and the paths `/terra/mqtt` and `/terra/api/monitoring/history`. Build images, public artifacts and MQTT wake messages contain no runtime credentials.

Enter real values through GitHub’s secret form or private files outside this checkout. Disable runner debug logging for production jobs. The GitHub package token is short-lived and the VPS uses a temporary registry login. Grant the repository’s Actions token access to its GHCR packages.

| Environment secrets | Contents |
| --- | --- |
| Production — `VPS_HOST`, `VPS_USER`, `DEPLOY_KEY`, `VPS_KNOWN_HOSTS` | SSH deployment destination, restricted private key and independently verified host key entry. |
| Production — `BROKER_MONITOR` | JSON object containing `host`, numeric `native_port` and `ws_port`, and the release publisher’s `username` and `password`. The hostname must match the TLS certificate. |
| VPS — `WEB_PORT` | Free loopback port for containerized nginx. |
| VPS — `DASHBOARD_URL` | Full public HTTPS dashboard URL. Omit for the first side-by-side staging, then set after ingress cutover to verify the public asset set matches the candidate. |
| VPS — `BROKER_VOLUMES` | JSON object with `data` and `logs` naming the two existing external Docker volumes. |
| VPS — `BROKER_CERT`, `BROKER_KEY` | Broker’s PEM full chain and matching unencrypted PEM server key. Redeploy the broker when renewed. |
| VPS — `BROKER_PASSWORD_FILE`, `BROKER_ACL` | Mosquitto password-file hashes and the complete topic ACL. Generate the password file interactively with `mosquitto_passwd` in a private directory. Use [acl.example](vps/acl.example) as the role template. |
| VPS — `MONITORING_DASHBOARD_USER`, `MONITORING_CONTROLLER_USER` | Optional MQTT account names for custom ACLs where the workflow cannot identify the two roles. |
| VPS — `MONITORING_SETTINGS` | Optional existing collector configuration. Use a JSON object with `mqtt_user`, `mqtt_password` and `dashboard_user`. `history_days` sets retention from 1 to 1,825 days (default 1,825). When supplied, the corresponding accounts and permissions must already be in the broker secrets. |
| Pi — `PI_SETTINGS` | JSON object containing `host`, numeric `port`, `username` and `password` for the controller. The managed controller validates TLS using the system trust store or the CA path in its live YAML. Use a system-trusted CA for the updater and monitor. |
| Pi — `RELEASE_SIGNING_KEY`, `PI_RECIPIENT_CERT` | RSA private signing key in PEM format and the Pi’s public RSA encryption certificate in PEM format. The private device key stays on the Pi. |

Use separate identities for the controller, browser, monitoring collector, updater and release publisher. Store each secret in the environment listed above. For credential rotation, introduce a second authorized broker identity, publish the new controller settings, verify its acknowledgment and then retire the old identity. Keep rollback credentials valid through the release window. Bootstrap identity rotation for the updater uses its private configuration on the device.

## Prepare the VPS once

1. Install Docker and the Compose plugin. Reserve the external network name `terrapi-app` and Compose project `terrapi` for this application. Save the original nginx route, broker image, port mappings and restart procedure. Back up the broker's configuration, password database, certificates and actual data and log volumes consistently. Test restoration with separate copies. Rehearse on unused ports with those copies.
2. Install `deploy/vps/apply.py` as root-owned executable `/usr/local/lib/terrapi-vps/apply.py`. Install `frontend.yaml`, `broker.yaml`, `monitoring.yaml` and `mosquitto.conf` beside it, root-owned. In that directory create a root-owned `image-namespace` file holding `ghcr.io/<lowercase-owner>/<lowercase-repository>`, and `allowed-volumes.json` matching the private volume secret. Only the operator can change these allowlists and helpers.
3. Create a dedicated SSH account without Docker group membership. Give its deployment public key the authorized-keys options `restrict,command="sudo -n /usr/local/lib/terrapi-vps/apply.py"`. Use a sudoers rule scoped to that executable with **no arguments**. Example rule for a dedicated account named `terrapi-deploy`: `terrapi-deploy ALL=(root) NOPASSWD: /usr/local/lib/terrapi-vps/apply.py ""`. Lock down the account to key authentication.
4. Deploy **frontend** and check the loopback URL under `/terra/`. The first frontend can be staged beside the live site. During broker handoff, release its two old port bindings by stopping only the existing TerraPi broker. Deploy **broker** using the existing volumes and ports. The managed native listener requires TLS, even on 1883. A Pi previously using plaintext needs to switch in the same window.
5. Have the shared HTTPS ingress proxy the entire `/terra/` prefix, preserving the path, to the frontend loopback port. Forward HTTP/1.1 WebSocket Upgrade and Connection headers. Redirect HTTP to HTTPS before users sign in. Validate and reload the shared configuration, then exercise the dashboard route, its assets, WebSocket login and fresh sensor data from outside. Keep the prior ingress route and container until the new deployment is verified.

The internal Docker WebSocket listener is reachable only on the application network. The separately published TLS WebSocket listener supports existing clients. The broker release checks authenticated TLS connections over both transports. The frontend release checks HTML and its current JS and CSS, and retains old hashed assets for open browser tabs. Docker changes use a service-specific Compose command. On the first migration, recovery uses the saved legacy container and state. After the first managed release, a failed health check reapplies the previous service definition. Restoring broker data across incompatible formats requires a compatible backup.

## Enable monitoring on a managed deployment

Run **Deploy** using a build that includes monitoring. The VPS job extends the broker configuration from `BROKER_PASSWORD_FILE` and `BROKER_ACL`, identifies the existing dashboard and controller accounts by their ACL rules, and creates the dedicated `terrapi-history` collector. It sends the updated broker configuration and collector settings through the existing deployment entry point. The credential stays stable across runs using the same `DEPLOY_KEY`. Run Deploy after rotating that key so both services receive the new collector credential. The base GitHub secrets are unchanged. [ACL template](vps/acl.example)

The VPS entry point installed during provisioning must support the monitoring service and have `monitoring.yaml` beside it. Compose creates the named volume `terrapi_monitoring_data` on first start. Before updating the frontend and controller, the workflow verifies the collector's broker subscription. The first minute of data appears after the upgraded controller reports.

The dashboard account must have a Mosquitto 2 PBKDF2-SHA512 password hash in `BROKER_PASSWORD_FILE`. After a dashboard password rotation, run Deploy to refresh both the broker and history service. The current dashboard credentials authorize history reads even when the broker is unavailable.

The controller samples once per minute and keeps up to 14 days of unacknowledged observations on the Pi. Each acknowledgment follows a successful database commit. The VPS keeps temperature and humidity as scaled integers, packs equipment and connection flags together, and maintains hourly statistics for long-range queries. Five years of synthetic minute readings and hourly statistics used about 43 MiB after SQLite checkpointing. Allow additional space for the journal, logs and image. Time with no readings takes no space in the sample table. Each history request returns up to 1,200 chart buckets across at most five years. Zooming back to a short range retrieves the underlying minutes. Reducing `history_days` prunes older observations on startup. SQLite returns spare pages to the filesystem in batches and keeps some available for new readings. Choose the retention before deploying a smaller value.

History survives container and image changes in `/data/history.sqlite3`. To back it up, stop the monitoring container briefly and copy the entire `terrapi_monitoring_data` volume to separate storage, then restart monitoring. Restore a consistent volume copy while the recorder is stopped. The controller queues readings during the interruption. Docker rotates the recorder's logs at 1 MB and keeps two files.

## Pair the Pi once

Prepare a trusted LAN maintenance session. Keep the running manual controller, its original config and a way to restart it until the managed baseline is verified. The supported target is a 32-bit ARMv7 Pi with Python 3.9, systemd, OpenSSL, venv support and working GPIO access through the `gpio` group. Install the dependencies in [requirements-pi.txt](../backend/requirements-pi.txt) where the service account’s system Python can import them. The updater uses the system Paho installation independently. Check GPIO device permissions and the configured timezone. Keep signing and bootstrap files outside Git.

1. Generate an RSA signing key outside the checkout, store it in `RELEASE_SIGNING_KEY`, and export its public key as `signing.pub`. Generate the device encryption key `recipient.key` and a matching self-signed RSA certificate `recipient.pem` on the Pi. Store only that certificate in `PI_RECIPIENT_CERT`. Example commands in private directories with `umask 077`:

   ```sh
   openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out signing.key
   openssl pkey -in signing.key -pubout -out signing.pub
   # On the Pi
   openssl req -x509 -newkey rsa:3072 -nodes -days 1825 -subj /CN=controller -keyout recipient.key -out recipient.pem
   ```
2. In a private directory on the Pi, place `signing.pub`, `recipient.key`, `recipient.pem`, and `settings.json` matching the initial private `PI_SETTINGS`. Add `updater.json` with the release directory's HTTPS `origin` (ending in `/terra/releases`), broker `host`, numeric native `port` and dedicated updater `username` and `password`. Optional `health_timeout` is in seconds and should cover several sensor reporting intervals. Use a root-only directory and file mode 0600 for secrets.
3. Run `sudo /usr/bin/python3 deploy/pi/bootstrap.py /path/to/working/backend /path/to/live/config.yaml /path/to/private-pairing`. It prepares the last working code as release 0, copies live modes and schedules, enables TLS in the managed copy, and installs the services without starting them. Pause dashboard edits during handoff and capture the intended manual mode. Dependencies from a personal Python user site need to be made available to the service account before handoff.
4. During the coordinated broker cutover, stop the manual controller, start `terrapi-controller.service` and verify fresh readings, mode and relay state. Once verified, enable it at boot and enable and start `terrapi-updater.service`. Only one process should own GPIO. The first supervised rollback returns to release 0. The original manual startup remains the fallback if the managed baseline itself fails.

## Controller release and recovery

The production workflow signs a manifest covering the release, sequence, target, expiry and SHA-256 hashes. It encrypts the controller's settings to that Pi, then sends only encrypted settings, signed metadata and source to the VPS release directory. The VPS publishes a fixed MQTT wake message. The Pi also checks the same HTTPS origin on startup, reconnect and every minute. It rejects tampered data, unexpected archive paths, incompatible targets and stale requests.

Before switching it checks credentials, creates a release-specific environment using the Pi’s installed native stack and verifies the exact direct dependencies. When a pin changes, an unprivileged build account installs available binary wheels into the candidate environment before activation. Missing ARM wheels or native OS libraries require provisioning during maintenance. The running environment stays available during staging. Live YAML stays outside release directories. Two reporting intervals must complete with confirmed command subscriptions, a relay snapshot and fresh temperatures for all enabled thermostats in the active mode. A boolean-only or empty profile requires at least one finite temperature. New controllers persist the manual selection. An older YAML without a selection starts manual operation with all relays off. Recheck the intended selection when rolling back to an older controller. A failed activation switches back locally. A journal records the previous release before activation so recovery can run after power loss even with the network down.

On an already paired Pi, install the updated `deploy/pi/updater.py`, `deploy/pi/check_candidate.py` and `backend/terrapi/config_schema.py` as root-owned files in `/usr/local/lib/terrapi/` during maintenance, then restart `terrapi-updater.service`. The bootstrap installs them on new devices. The updater checks for 64 MiB of free staging space, validates the live YAML and tests the controller’s credentials and CA as the service user. Permanent preflight failures end that sequence. Transient preparation failures get three attempts. A new deployment number starts a fresh attempt after remediation. Activation syncs the candidate filesystem, journal and release link before reporting success.

Revision-checked editing becomes available when the controller finishes updating. Older dashboard clients may still send single-section edits. Existing browser credentials are cleared on the first visit to the new dashboard. Confirm rotation of the previously exposed MQTT and SSH credentials in private operator records and retire any remaining old credentials after verifying the replacements.

CI waits up to five minutes for a matching Pi acknowledgment. A timeout means the result is unconfirmed. A disconnected Pi can still apply that request within its 24-hour validity. Rerun the same workflow run to check the same request, or submit a new deployment to supersede it. To roll back, choose the earlier build run in a new **Deploy** run. Reusing a previous artifact creates a new signed deployment number. Retain older successful releases and compatible broker backups for the rollback period. Review free space on the VPS and Pi before repeated releases.

For local verification, run the frontend tests and build, `python -m unittest discover -s deploy/tests` and `python -m unittest discover -s monitoring/tests` in an environment with Paho MQTT 1.6.1, PyYAML and Mosquitto, and the Docker smoke test commands in [.github/workflows/ci.yml](../.github/workflows/ci.yml). All smoke-test credentials and certificates are disposable.
